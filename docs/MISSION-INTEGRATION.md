# Serial integration and provenance — 2026-10-03

Completed prefix sources, full author history, exact integration chain, actual pinned check exits and receipts, and integration metadata identity authorize one complete next-wave binding. Fixed local check effect intent/receipt handling is shared; checkpoint callers cannot supply commands, coverage adapters or a fabricated selected result. A checkpoint retains all history, never grants readiness and never refills budgets. See [assignment scheduling](ASSIGNMENT-SCHEDULER.md) and [strict v3 compatibility](decisions/2026-10-03-supervised-runs-v3.md).

Task 11 adds optional strict v3 run fields. Old records remain readable; absent history cannot certify authorship. Back up authority before upgrading. Backups retain these fields and Git worktrees; rollback needs a compatible release or an explicitly reconciled pre-upgrade profile, never deletion of evidence or restoration over active work.

`integrations` is a maximum 32-entry history. Each record binds id, assignmentId, workspaceId, workerBase, workerHead, workerFingerprint, commits (1–256 literal object IDs), changedPaths (maximum 5000), before source, time and state (pending/completed/conflict/unknown). Optional after source, resultingCommits, error and command {id,state:pending/running/completed/unknown} retain the outcome. Intent is durable before the single cherry-pick command. Worker snapshots must be clean, exactly at the assignment base/head, linear, and restricted to owned paths. Both rename endpoints, deletions and all intermediate commit paths are inspected; policy segments .git/.agents/.codex are forbidden case-insensitively. Rejected bytes remain in the worker. Conflict bytes and both heads remain in the integration worktree and receipt. No reset, ours/theirs preference, retry or automatic cleanup occurs.

`authorHistory` is a maximum 256-entry append-only history of {id,taskId,provider,time,state:pending/ready/unknown,threadId?}. Main persists the pending entry before session creation and the ready thread identity before any writing turn. Missing or unresolved history, old unobserved sessions, extra commits and ambiguous session identity fail closed. History is independent of invalidatable verification. Base source is the captain-approved starting snapshot; all subsequent integration commits require this history and retained integration receipts.

`combinedChecks` is a maximum 1000-entry history of {id,workspaceId,source,criterionIds,kind,state:pending/completed/unknown,time,result?}. Result stores the actual bounded MissionEvidence execution receipt, including before/after fingerprints and exit status. `repairProofs` (maximum 256) binds {id,findingId,reviewId,checkId,source,time}; only a trusted main verifier may install a finding-specific passing regression receipt. A generic script or model assertion does not prove arbitrary criteria or fixes. The main-only verification API accepts a trusted coverage adapter; there is no provider/renderer installer. Missing coverage, missing selected result/artifacts, unsupported playable proof and incomplete history remain blocked.

One physical and logical integration reservation is held through effect and durable receipt. Recovery reconstructs pending/unknown/conflict reservations independent of task status. A lost command response or failed receipt keeps the operation unknown and reserved; no automatic reconciliation or retry. The shared Task 12 stop path can inspect `Hub.integrationCommands()` and use the exposed owned command controller. It must persist its shared stop intent first. Cancellation never proves Git did not run and cannot release unknown reservations.

Hub main APIs: `inspectWorkerResult({runId,assignmentId,head})`, `integrateWorkerResult({runId,assignmentId,head,expectedRevision,expectedSource})`, and `verifyCombinedSource({runId,expectedRevision,missionId}, trustedCoverage)`. Live supervision/tool containment stays disabled. These contracts are proved only with explicitly offline disposable repositories and providers. ## Resolution-v1 continuation — 2026-10-05

The following bounded continuation supersedes the historical Task 11 dispatch limitation above. Main exposes `prepareIntegrationResolution({runId,projectId,expectedRevision,operationId})` and `settleIntegrationResolution({...identities,repairAssignmentId,repairHead})`. The inputs identify retained authority; they never select paths, commands, owners or allowances. A known fresh conflict returned by `integrateWorkerResult` triggers preparation once. The generated repair's genuine finished outcome triggers settlement after releasing its task lock. Unknown or recovered operations are never automatically continued.

The original `state:'conflict'` and all original receipt fields remain historical and unchanged. An optional nested `resolution` contains version 1, id, runId, projectId, operationId, reserved ordinal, generated assignmentId, before source and monotonic state (`reserved`, `preparation-intent`, `prepared`, `applying`, `completed`, `unknown`). Preparation records prepareRevision, private bundle receipt `{id,sha256,bytes}`, managed workspaceId, and the assignment's `resolutionOwnership` receipt binding original assignment/workspace/source and bundle hash. Applying records settleRevision, frozen repair candidate and actual task/thread/turn author. Completion additionally requires observed zero-exit abort result, exact restored abortSource, actual resultingCommits and clean finalSource. Strict validators reject unknown keys, inconsistent bindings and incomplete terminal states. Exact duplicates use the original operation revision and cause no Git effects.

Reserve a generated assignment and repair ordinal atomically when a slot is available before charging the conflict, including the final slot. Exhaustion remains sticky. Only this reserved repair and subsequent exact combined checks and independent review may finish; another repair or improvement receives no additional allowance. Ordinary launch/time/token/worker limits and explicit stop remain authoritative. Older conflicts without a resolution-v1 reservation stay blocked; counters alone never mint an entitlement.

Capture all dirty/index/untracked paths and exact stage/current bytes, modes, blob IDs, original full range/diff, successful prefix, CHERRY_PICK_HEAD and sequencer state. Reject protected/out-of-scope paths, links, aliases, unrelated content and changed sequencer identity. Bounds: 256 commits, 5,000 paths, 1 MiB per file/blob, 8 MiB aggregate bytes and 16 MiB serialized storage; the complete untrusted author context additionally must fit 80,000 serialized bytes. No truncation. Main derives an exclusive private `conflict-bundles/<id>.json` under its profile root, fsyncs it and verifies readback before the receipt. Preserve that directory with the profile. The repair gets complete evidence as untrusted context and works only in its ordinary managed workspace at the original before head.

The original integration reservation remains held. Main issues a private in-memory gate capability for only that generated repair or its workspace creation; roots must be physically disjoint, every other lock remains effective, and recovered controllers cannot acquire it. The special ownership receipt permits this exact same-base handoff without mutating the predecessor's source result. Former-owner dispatch and late outcome are rejected.

After durable applying intent, main runs fixed `cherry-pick --abort`, verifies the clean exact original before source and absent conflict sequence, then revalidates authority and runs the frozen literal repair commits with existing hooks/signing/rerere restrictions. Cancellation between children prevents the second child. Any failed/mismatched command, lost acknowledgement, changed bundle/source or failed completion receipt retains unknown authority and its reservation. No reset, clean, second repair charge or automatic replay occurs. Restart keeps pending preparation/application disarmed, including when HEAD happens to match; matching source is not observed process exit.

One effective-contribution predicate recognizes ordinary completed integrations or strict completed resolutions. For resolution, the aborted original prefix remains historical; only the actual repair result range contributes to the continuous integration-base-to-final proof. Both original and repair authors remain reviewer exclusions. A sanitized main projection exposes only generated assignment ID and prepared/completed display state; it grants no renderer authority. Resolution is not readiness, review approval, Play evidence or captain acceptance.

Shared crew/capacity release also wakes a blocked run only when its exact prepared generated repair remains queued without a task or launch reservation and the existing live-controller admission still succeeds. It does not wake ordinary blocked or recovered work. Completed resolution classification reuses the strict receipt validator: the original command must be completed and bound to its operation, and the unique nonempty resulting range must have the candidate's count and end at the final source head. Contradictory persisted completion remains unresolved for recovery fencing, budget and display.

The physical single-row SQLite TEXT schema and WAL/FULL are unchanged. These additive JSON fields require a resolution-v1 capable reader/writer; older strict versions fail closed. Preserve the current profile and verified backup before updating. After new writes, rollback must retain the latest authority and private bundles. Restoring a pre-resolution backup would lose evidence and is not transparent rollback. Pure adapter fault checks are distinct from real Git/provider fixture evidence; neither certifies live provider containment or the final complete mission journey.

`integrationCommands()` includes both active integration commands and combined checks. Controllers have id/reservationId/runId/workspaceId/kind/state/exited, an observed pid while running, and cancel() when a process is owned. A cancellation request is distinct from process close. Check cancellation uses the existing checked process-tree cleanup path; Git cancellation requests a process signal and its outcome remains unknown. Recovered controllers expose no invented PID or cancel function and keep exited=false. Task 12 must use its shared durable stop/reconciliation policy; no second run-control dispatcher is introduced.

Coverage adapters are main-owned functions, unavailable through IPC or provider tools: `coverage({kind,result,source,criteria,root})` returns criterion IDs established by that actual execution; `repairCoverage({kind,result,source,findings,root})` returns findings established by a specific passing regression or direct artifact inspection. No default mapping promotes a generic npm success to criterion proof. Missing adapters yield retained execution receipts but no criterion certification. Playable checks are unsupported here and remain missing until the downstream playable verifier exists. This is intentionally narrower than claiming arbitrary criterion understanding.

Review correction: every unused queued reviewer (no task, workspace or launch reservation) is pinned in one durable handoff to the verified combined head before dispatch. Remaining criterion reviews may dispatch during the reviewing phase; that phase admits only review assignments and stays reviewing when reserving one. Partial approval never grants readiness or opens implementation admission. Capacity release uses the existing Task 10 wake path. Definitive rejection before a combined-check intent becomes durable releases the temporary reservation and creates no controller. An uncertain intent acknowledgment retains an unknown record/controller and reservation even when its submitted image has not been published into live state. Storage schema and rollback requirements are unchanged.
