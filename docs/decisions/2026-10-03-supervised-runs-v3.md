# Supervised runs in MissionBook v3 — 2026-10-03

## Decision recorded before implementation

MissionBook version 3 adds a required dense `runs` array. Empty books use v3. Workspace version remains 1; existing workflowVersion 1 attempts retain their original interpretation. This change stores and validates authority only: it provides no supervised dispatch method, scheduler or runtime admission. Reliability Task 3 remains blocking.

`inspectMissionProfile` returns `empty`, `v1-upgrade`, `v2-upgrade`, `v3`, or `unsupported`. A v1 upgrade first applies existing workspace/legacy acceptance semantics, then adds empty runs. A v2 upgrade changes only book version and adds empty runs. Root, book and mission compatible unknown fields, task transcripts, drafts, exact result hashes and acceptance receipts remain intact. Legacy profiles containing reserved new authority fields are rejected instead of erasing them.

## Backup, migration and rollback

Upgrade requires an exclusive, fsynced full-state JSON backup, verified by rereading exact serialized input bytes and SHA-256. The receipt is rechecked immediately before first save. Backup failures/tampering block writes. The prepared image is not written on read. Only the existing persistence worker commits it atomically (SQLite WAL/FULL transaction, or fsynced same-directory JSON rename). Both original authority and serialized authority are checked before commit. Unsupported files are rejected before opening a writer. This migration never changes actual user profiles during development.

Rollback means disable new dispatch in a compatible v3 reader and preserve current records. Never open v3 with a v2 binary and never restore an older backup over current work. Old profile inspectors reject version 3 even if reservations are otherwise opaque. Alternative of adding runs under v2 was rejected because old readers could ignore live reservations.

## Stored contract

SupervisedRun version 1 has id, projectId, missionIds, nonnegative safe-integer revision, phase, grant, counters, assignments, workspaces, reviews, readiness (nullable), decisions, improvementTriggers and stopIntent (nullable). Phases follow the approved plan. IDs are nonempty bounded strings (200 code units), arrays are dense with unique record identities. A book has at most 1,000 runs; a run at most 1,000 mission links, 32 assignment/workspace records, 256 reviews, 1,000 decisions and 256 improvement triggers. These storage bounds do not grant execution allowance. Unknown authority fields in new records reject; compatible opaque fields in existing roots/books/missions are preserved.

Grant has id, optional version/revision (positive/nonnegative integer), createdBy captain, scope with projectId/objective/activities and optional standingImprovement string. Activities are allowlisted local read/write/test/build/review/research/integrate. Approved ceilings: workers 3, initial assignments 16, launches 32, repairs 3, workerMs 900000, activeMs 3600000, tokenLimit 100000, improvementMs 300000, improvementTokens 10000. Positive integral lower limits are allowed, improvement limits may be zero. Counters launches/repairs/activeMs/tokens/improvementMs/improvementTokens are nonnegative safe integers and may exceed a subsequently lowered grant or soft telemetry threshold; no normalization resets them.

Assignments contain id/crewId/roleId/capability/objective, ownedPaths/dependencies/criteriaIds, baseCommit, state and optional taskId/workspaceId/launchReservationId/sourceResult. States: queued, reserved, starting, working, waiting, unknown, finished, failed, interrupted, cancelled, blocked. Dependency references resolve within the run and cannot self-reference. Workspace refs contain id/projectId/runId, assignmentId or integration:true, canonicalRoot/gitCommonDir/branch/baseCommit/state. They are storage identity, not permission to use a path. Privileged consumers must verify canonical paths afresh. Sources contain baseCommit/headCommit/fingerprint/artifactHashes (path/sha256 records). Reviews bind run/assignment/reviewerTask/source with decision approve/request_changes/blocked, findings and time. Readiness binds source/reviewIds/criteriaIds/time; it does not create captain acceptance. Decisions are bounded run events with identity/revision/type/time and allowlisted string details plus option, reason, dissent (bounded string array), owner, nextAction and reopenEvidence. Improvement triggers bind id/kind/sourceId/time; kinds are completed_result, user_feedback and new_verified_evidence. Later accounting/reservation or readiness service additions must extend this strict schema with their own tests before writing new fields. Stop intent binds id/requestedBy captain or policy/reason/time/revision. Nested schemas are validated before normalization.

Mission `runId` is optional and reciprocal with run.missionIds in the same project. Task runId/assignmentId/workspaceId is optional for legacy tasks; any new binding must resolve to a run/assignment/task in that project and any workspace must match that assignment. Duplicate task identities referenced by supervised work are rejected. MissionBook construction validates book-local links; profile inspection additionally validates task links. Every review resolves to exactly one task in the same run/project with a bound reviewer-role assignment. Profiles without a mission book remain legacy-compatible only when tasks carry no supervised run/assignment/workspace authority.

Public shared types describe only sanitized run/assignment summaries. Private grants, accounting records, workspace paths and stop internals are not added to renderer state or transport.

## Failure and compatibility evidence

Tests cover exact v2 backup and full-state preservation, frozen old-reader rejection, sparse arrays, duplicate IDs, project/mission/task disagreement, future versions, invalid counters, grant bounds, worker roundtrip and worker rejection without overwriting acknowledged state. Frozen workload source/protocol bytes remain unchanged: compatibility loaders map validated historical v2-upgrade mode to the fixture's old v2 assertion, then produce a v3 in-memory fixture before current persistence submission. This is confined to fixture adapters; real profile migration still requires a verified backup.

## Ordinary reply delivery (Task 18 core)

The approved `task-18-ordinary-journey-design.md` defines the additive contract before implementation. Physical storage and book version remain unchanged. New ordinary runs retain a main-derived `ordinary` check plan/checkpoint, a `currentEpoch`, bounded stale-call receipts, and bounded delivery records. A delivery pins its production/review assignment sets, graph/criteria/grant/check-plan digests, genuine reply candidate, selected result and fresh validation coordinator. Assignment, verification, verdict and readiness `reviewBinding` fields bind the exact epoch, mission/attempt, delivery/continuation, selected result hash, source digest and complete required reviewer set. A validation task uses an exact delivery/workspace/execution binding rather than pretending to be an assignment or implementation author.

The current strict reader validates every additive record and cross-record task/result binding. Older strict v3 readers reject the added run authority fields rather than ignoring unfinished work. No database-engine migration or live-profile change is needed. Preserve the newest full profile, its backups and receipts before switching binaries; rollback uses a compatible non-dispatching reader that retains these fields, never an old backup over current work. Restart marks unfinished delivery records unknown and holds the existing task/effect/workspace reservations. It never replays a saved integration, selection, check or continuation dispatch.

A normal public goal now sends canonical bounded session context and role-specific tools. `sunny_status` refreshes an exact bound session; mutations compare the current revision and retain stale rejection receipts. Production delivery integrates genuine worker Git outcomes, waits for the production coordinator's real completion and selects a genuine worker message. Main then launches one distinct validation coordinator under the same cumulative grant. Its fixed `project-suite-v1` plan hashes existing npm test/build/typecheck recipes and consumes actual exact-source check receipts. Suite execution covers technical execution only; every pinned independent reviewer must explicitly review semantic criterion fulfillment. All required approvals establish source readiness; real reviewer and validation-coordinator completion plus quiescence are still required before acceptance.

Local tool waits return pending after 30 seconds and can rejoin using a refreshed context/new call ID; close, disconnect and control cancellation settle local waiters before owned operations drain. Such local settlement never proves a remote process stopped. Unknown submissions retain conservative telemetry/checkout fences. The only pre-turn telemetry distinction is a main-held exact binding after acknowledged fresh thread creation and before any durable turn intent/submission; it still occupies capacity and spends its launch.

### Checkpoint-wave additive contract — 2026-10-06

Newly created ordinary runs add `ordinary.checkpointWaves:1`. Plan admission stores `currentEpoch.productionWaves` with version 1, original graph records and bases, their digest and at most 16 ordered membership sets. Delivery `productionWave` stores version, plan digest, active wave, at most 15 completed checkpoints and an optional pending operation. Assignment `checkpointBinding` pins epoch/delivery/checkpoint, generation/digest, successor wave, source head and integration workspace identity. Records lacking the capability retain the original dependent-wave rejection; no migration invents historical proof.

Each strict prefix proof retains version/id/epoch/delivery/generation/wave, graph and check-plan digests, assignment/task/workspace/source references, exact integration/check receipt IDs, the complete successor set, full source, workspace ID and metadata digest. Completed proofs add a digest and require durable passing fixed-suite receipts. Final source/result/review authority remains separate and exhaustive. All arrays are bounded and unknown keys reject. The physical SQLite single-row format and WAL/FULL remain unchanged. Back up before upgrading; old strict readers fail closed. Rollback preserves the newest profile and receipts with a compatible reader, never by erasing fields or restoring old authority over current work. Playable and later-epoch completion remain separate acceptance stages.
