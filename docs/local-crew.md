# Local crew developer — 2026-11-04

Decision: add an optional local advisory workspace to each crew journal. Franky is the initial senior developer helper. Each character retains its identity, selected local model and explicit engineering skill instructions. Existing Codex missions remain the execution path; local chat has no command, file-write, browser or delegation tools. Skill selection is guidance, not evidence of senior-level capability.

## Persistence contract (before implementation)

Add optional top-level `localCrew: {version: 1, profiles: {...}}` to the existing saved state and manual backup. A profile contains `model`, an allowlisted `skills` array, project-scoped `sessions` (up to 20), and project-scoped conversation messages (up to 40 per session). Sessions record status, error and model attribution. Missing data initializes lazily; no old tasks or memories are migrated. Working sessions recover as interrupted, never automatically replayed. Existing growth journals retain explicit notes and attributed completed local exchanges; no model weights are changed. Local notes are project-scoped.

Compatibility: additive state only, no SQLite schema change. Old binaries ignore this field and may drop it when saving. Before activating a new build, export the existing profile using Settings → Export backup. Before downgrading, export again and preserve that backup; never restore an old profile over current work. Rollback is switching back to the prior binary with the exported localCrew data preserved separately. There is no automatic backup import or model training.

Failure checks: absent/malformed state, persistence failure before network access, missing model, remote-model rejection, malformed/oversized response, timeout, cancellation, no completion after cancellation, restart without replay, project/crew isolation, correction, disabled recall, export and reset.

Local lessons and episodes carry `source.localOnly: true` in the existing growth journal. Default Codex and router retrieval exclude these items; the local adapter explicitly requests local recall. Editing a local note preserves that boundary. Local chat recalls pinned global captain preferences and this project's pinned lessons; generated conversation episodes are excluded from cross-conversation recall. Older binaries do not understand the localOnly boundary: do not open the new profile in an old binary if preserving local-only recall is required; retain the backup separately when rolling back.

## Runtime boundary and use

Reliability/recall follow-up design, 2026-11-04: keep unanswered/interrupted questions in the visible transcript but exclude them from future model context. Send only complete prior user/assistant pairs within the existing history budget, followed by the current question; never send an orphan assistant message. A clearly failed initial write restores the prior conversation. A clearly failed completion write removes the unsaved answer and undoes only its learning, preserving concurrent journal edits and explicit forgetting. An uncertain or already-durable write retains its evidence and requires storage recovery before further inference; it must not be silently rolled back or retried. Add a read-only recall preview showing the same bounded journal selection used for the current question. No persistence schema change or additional model calls; existing backup/rollback applies. Recompute previews when the project, question or journal changes.

Follow-up design, 2026-11-04: add an explicit project-relative source preview with numbered lines, read timestamp and SHA-256 provenance. Preview reads one bounded UTF-8 source file through the existing guarded reader; it does not contact a model. The captain inserts the preview into the question and can edit/remove it before sending. The text is then retained as ordinary local conversation text under the existing bounds; there is no new persistence schema or automatic repository scan. Protected directories, secret filenames, symlinks, hard links, binary/invalid UTF-8 files and oversized reads are rejected. A line range is a saved snapshot, not a claim that the file remains unchanged. Unsent previews are discarded on project changes; drafts remain project-scoped.

Open Crew → a character's journal → Local developer. Select a registered project, refresh installed models, choose a model and skills, then save the setup. Paste the code/error/diff you want reviewed, or open **Add a project file**, enter a project-relative path and starting line, preview it, then add the displayed text to your question. The helper receives that text, recent conversation from this project, and relevant pinned journal lessons. It cannot independently browse the repository or run tests; requested code and commands are drafts for review. Use existing missions when you want execution.

The main process contacts only `http://127.0.0.1:11434`, rejects redirects, checks the installed model and its local GGUF metadata before sending conversation content, and never pulls models or falls back to cloud. Ollama must be installed and running separately with a downloaded local model. Disable Ollama cloud features (`OLLAMA_NO_CLOUD=1`) as defense in depth. Sunny cannot attest to a modified third-party local server's behavior. Runtime discovery uses the live model catalog, not hardcoded model availability.

Only one local reply runs at a time. Stop aborts the local HTTP request and marks the session interrupted; actual server resource release depends on Ollama. A two-minute deadline and bounded input/output prevent unbounded requests. Successful replies become attributed recollections only when the existing memory toggle is enabled. Teach correction pins an editable project-specific note. Existing journal controls edit/forget it. Clear conversation removes its local transcript; separately forget journal memories to remove cross-conversation recall. Manual backup includes both. Nothing runs continuously in the background.

Alternatives: ten resident models multiply memory demand; online weight updates risk learning erroneous outputs and need curated evaluation. Shared local weights plus independent persistent profiles provide the requested personal continuity first. Fine-tuning is deferred until representative tasks show measurable benefit.

Runtime compatibility decision, 2026-11-05: a live Qwen3.5 response exhausted the bounded output budget before producing a complete answer. Read the installed model's `/api/show` thinking controls. Request `think: false` only when `thinking.values` explicitly contains boolean `false`; otherwise retain the server's default. Do not infer support from a model name or capability label. Keep the existing deadline, answer limit, local-only check and rejection of incomplete replies. This adds no persisted field and does not store reasoning traces. Reference: [Ollama thinking controls](https://docs.ollama.com/capabilities/thinking).

Local identity decision, 2026-11-05: reuse the canonical character personality with an advisory-only role prompt. Do not import the executing mission prompt's instruction to inspect repositories and run tests into a tool-free local chat. Existing mission prompts remain unchanged. Review skill guidance explicitly covers path-segment containment, symlinks, check/use races, uncertain remote effects and confirmed idempotency before retries. These are instructions to the model, not enforced guarantees about its answer quality.

Protocol references: https://docs.ollama.com/api/chat and https://docs.ollama.com/api/tags; local-only configuration: https://docs.ollama.com/faq.

## Isolated launch and repeatable live check

The feature includes a separate real-local preview entry point. It uses `.sunny-dev/local-crew-preview-profile`, an ordered JSON store, a single-instance lock and the production renderer/local service. It opens Franky's local journal; the other nine main crewmates are independently configurable. No cloud client is constructed, and mission/terminal/file-write IPC is denied. Source preview reads only explicitly selected files in this checkout. The normal installed Sunny profile and shortcut are not used. Export from this preview contains only its separate profile.

From the primary repository root, with this machine's verified portable runtime/model store under `.sunny-dev`:

```powershell
./scripts/start-local-crew-preview.ps1 -RuntimePath './.sunny-dev/ollama-0.40.14/runtime/ollama.exe' -ModelStore './.sunny-dev/ollama-0.40.14/models' -Model 'qwen2.5-coder:14b'
```

The launcher makes no downloads. It reuses an existing local Ollama server or starts the supplied executable with process-only `OLLAMA_NO_CLOUD=1`, loopback binding and the supplied model store. Closing the preview stops only a server this launcher started. An already-running server retains its own configuration. Add `-Check` for a hidden fresh-profile admission/UI check; it records evidence under `.sunny-dev/local-crew-preview-check-*`.

For an explicitly opted-in end-to-end model check, add both `-Check -LiveReplyCheck` to that launcher command. It submits a synthetic question through the actual chat form, waits for the real reply to render, verifies its model attribution, and saves the answer and screenshot in the fresh check profile. It never runs the generated answer. Plain `-Check` performs no inference. `-LiveReplyCheck` without `-Check` is rejected so test questions cannot land in an interactive saved preview profile.

For a repeatable real-inference check, start Ollama separately and run:

```powershell
node scripts/check-local-crew.cjs --model qwen2.5-coder:14b
```

It uses synthetic code and a unique isolated profile, checks a real reply, restart persistence, notes-only recall, empty cloud recall and cancellation. It records the response for review and **never executes generated code**. Passing establishes transport/state behavior, not engineering competence. Any installed local model can be selected explicitly; the example name is this machine's tested candidate, not a hardcoded application default.

### First useful conversation

1. Open Franky's **Local developer** tab. Under **Model and skills**, choose the installed model and the skills you want. Save personal guidelines such as: “Explain the cause, propose a small patch, and give complete runnable tests. Say what evidence is missing.”
2. Save the project's actual conventions under **Teach a correction**. For Sunny desktop work, a useful lesson is: “Desktop modules and tests use CommonJS on Node 24. Tests import `const {test}=require('node:test')` and `const assert=require('node:assert/strict')`. Use `test(...)`; do not call `t.end()`.” Use different conventions for another project.
3. Preview a relevant source file or paste a focused error and code excerpt. Ask for one bounded change, its failure cases and verification steps. The helper sees the supplied excerpt, not the entire repository.
4. Inspect **Memories for this question** if the answer seems to follow an old convention. Correct or forget the relevant pinned lesson, then clear the conversation to remove old answers from the current chat context. Clearing a conversation retains saved lessons.
5. Review the proposed patch and run its checks through your normal development workflow or an existing Sunny mission. Save a verified takeaway as a lesson when it will help future work.

Each crewmate has separate model settings, guidelines, conversations and lessons. Selecting a different model changes the engine for future replies; it does not erase that character's saved history. Replies retain their model attribution. One local reply runs at a time, so the ten profiles do not require ten models resident in memory.
