# Mission review reliability decision — 2026-09-30

Mission-task handoffs enforce the same reviewed-attempt continuation lock as direct follow-ups. A finished coordinated stage, review-ready attempt, or accepted attempt must start a new attempt from the Mission Board before more work can be dispatched. Ordinary conversation handoffs remain available.

Project check discovery is a read-only, mission-scoped `mission:checks` action returning only supported, nonempty npm script names (`test`, `build`, `typecheck`, `lint`). Discovery does not change mission revision or evidence. The renderer disables absent checks and rejects stale discovery responses after changing selection. Check execution revalidates package availability before acquiring a reservation or persisting execution intent, and the runner independently validates again immediately before execution. An unavailable script therefore cannot create failed acceptance evidence. Executed failed/stale checks and unresolved-process reservations still block acceptance.

An alternative was recording unsupported requests as failed checks. That falsely claimed execution and created an acceptance gate the captain could not satisfy. No artifact or mission event is recorded for a rejected preflight request; the caller receives the error. A package change after execution intent is persisted still fails conservatively, retaining existing recovery semantics.

No persisted schema, provider behavior, merge authority, or dependency changes. Existing saved evidence remains unchanged; this does not automatically erase historical failed checks. Rollback consists of reverting the source change and rebuilding, with no database restore.

Verification in the isolated clone based on d1779c2: handoff regressions failed before the guard and passed afterward; unavailable lint produced one failed artifact before preflight and none afterward, allowing acceptance. Full `npm test`: 370 passed, 0 failed. `npm run build`: passed (existing large-chunk warning). Native `desktop/mission-smoke.cjs`: passed including capability controls, real disposable npm check, uncertainty recovery, acceptance, persistence and reload. Provider/GitHub transport are synthetic fixtures; no live provider or publication occurred. Screen reader behavior was not tested.

Mission brief drafts reuse the existing `sunny:draft:v1` sessionStorage convention under `mission:brief:<projectId>:<field>`. Title, objective, criteria and completion boundary survive navigation and reload in the same window. The last selected project is window-scoped; an unavailable project falls back to the visible project list. Submitted values clear only if they still equal the saved draft, so a newer edit or another project's brief is preserved. Failed mission creation preserves the draft. Closing the window ends these drafts; this is not durable database storage or a backup. If browser storage is unavailable, in-memory editing remains usable but reload persistence is unavailable. No migration or private-profile access is required. Rollback leaves inert draft keys that can be overwritten by the restored UI.

PR descriptions can now be edited before publication through the revision-bound `mission:editPr` action. Only current prepared-preview identity, title (1–200 characters, one line), and body (1–60000 characters, null-free) are accepted. Source is revalidated, exact authored text is saved with a fresh preview identity and expiry, and any prior authorization is discarded. Repository, commit, source branch, target branch, and attempt identity are inherited from the verified preview. Stale revisions/preview IDs, publishing or uncertain state, and failed persistence fail closed. The renderer blocks publication with unsaved text and resets confirmation after editing or saving. Publication continues to use a literal argv title and UTF-8 body file; editing grants no external authority or mission acceptance. Existing saved previews need no migration. Rollback uses their existing fields unchanged.

Denied browser storage and quota failures no longer prevent a successful save from clearing matching in-memory brief text. A submission event carries the exact submitted value; each mounted draft compares its current value before clearing, preserving newer edits even when an older delayed save finishes after navigation. Storage clearing remains best effort and cannot promise persistence across reload while storage is unavailable. Native denied/quota fixtures reproduced the retained-brief bug before the fix and now cover successful clearing, failed-save retention, and newer in-memory draft preservation. Shared Home/Workbench workflow remains verified.

Publication now applies the same exact-text validation as preview editing before authorization is checkpointed and before direct publisher transport can push. Sunny uses a conservative 60000-character description cap; this is an application limit, not a claim about GitHub's exact limit. Generated previews with an oversized body or multiline title remain visible and editable so the captain can repair them. Invalid text leaves the preview prepared, creates no uncertain publication state, and makes no external calls. Tests cover the exact cap boundary, invalid generated text repaired to a new preview, and rejection before authorization persistence.
