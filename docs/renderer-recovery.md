# Renderer exit diagnosis and recovery

Revised 2026-09-30 against source at base `5c8c6cb`. The earlier version of this document described a renderer diagnostic fix and crash smoke that were absent from that checkout. Those historical claims are not current verification evidence; the earlier PR was not cherry-picked.

The original interface exit cause remains unknown. Historical startup logs record four renderer exits and one renderer error without reason, exit code, surface or build identity. A restricted-executor launch produced GPU exit `-1073741515` and `ERR_FAILED`, while an escalated desktop sample rendered. That environment difference does not identify the user's spontaneous crash cause. No change here claims to fix that crash.

## Bounded local diagnostics

Both the full hub and desktop companion now attach the same `desktop/diagnostics.cjs` lifecycle handlers. Main-frame load failures retain the integer error code; aborted loads (`-3`) and subframe failures are ignored. Renderer exits retain an allowlisted Electron reason and safe integer exit code. Unknown reasons become `unknown`. The renderer-error IPC derives surface from the validated sender, never from renderer-supplied metadata.

Every available event includes application and Electron versions, plus the source build stamp generated by `npm run build`. The stamp holds a SHA-256 fingerprint of allowlisted runtime source inputs, Git HEAD and a dirty flag. Hidden/private environment files, generated directories and symlinks are excluded. It is a source-input identifier, not an executable hash, signature or attestation. Preserve the packaged `dist/build-info.json` with the package/executable hash when comparing incidents. Missing or malformed stamps are tolerated and leave the source build identity absent; they do not prevent startup. Direct Vite builds require the separate `node scripts/write-build-info.cjs` step to produce the stamp.

The existing bounded local startup log rotates above 128 KiB. Prompts, replies, URLs, paths, raw exception messages and arbitrary properties are excluded from these diagnostic records. No network destination, crash dump, credentials or telemetry framework was added.

## Explicit recovery

For either renderer surface, the recovery dialog reports sanitized reason/code and offers Reload Sunny or Keep closed. Dismissing the dialog selects Keep closed. A reload requires an explicit response and is suppressed if shutdown or surface destruction occurs while the dialog is open. The smoke-test launch retains its existing no-dialog behavior.

Reload reattaches that renderer to the existing main-process Hub. It does not reset state, restart tasks or authorize another attempt. Saved unknown tasks retain checkout reservations; use status reconciliation before continuing possibly running work. Permissions, provider configuration and process memory limits are unchanged.

## Evidence and remaining verification

The new deterministic tests first failed on missing metadata, missing companion lifecycle handling and absent dialog cancellation/shutdown guards. They now pass, including private-field/log-injection rejection, both surfaces, ignored aborted/subframe loads, explicit reload, dismissal, destruction and quitting.

`desktop/reliability-smoke.cjs` is a standalone native fixture: it creates its own temporary Electron profile and JSON store, uses the real Hub with an unavailable fixture provider, forces a renderer exit on hub and companion, and verifies unchanged saved task state, retained unknown checkout ownership and zero provider requests after reload. Its automatic dialog choice exists only in that fixture. Run it with Electron after a build; never force a crash in the normal profile. Normal desktop execution of the fixture passed both forced crashes: each surface recorded reason `crashed`, exit code `2`, then loaded again; saved task state and unknown checkout ownership remained unchanged with zero provider requests. The clean run had empty stderr. Restricted execution failed during initial GPU startup before the intended crash test. Final package-level checks and exact fixture artifacts are recorded in the current handoff.

## Compatibility and rollback

No persisted state schema or migration changes. Existing timestamp/event lines remain readable; new lines append bounded JSON metadata. Revert the focused diagnostic/main/build-stamp changes or use the previous package. Keep the current profile; do not restore an older backup over mission data. For a fresh incident, retain timestamp, surface, reason/code, build stamp, exact package hash and whether the process was frozen, reloaded or exited.
