# Reviewed result saving — 2026-10-12

The captain authorized a three-hour reliability work session following the baseline proposal. Scope is the existing mission skill selector and Morgans reviewed-report save flow. The implementation stays in the existing Hub, JSON state and guarded local vault; no runtime replacement, routing expansion or workshop changes.

## Decision

Add a `resultSaves` array to the persisted Hub state. Each record binds a registered project, task, final assistant message ID and hash, optional mission/attempt identity, the captain-reviewed title/text, review time, operation UUID, canonical vault, exact reserved note path, intended note hash and save status. A saved record includes a receipt with operation ID, path, hash, byte count and verification time. The UI renders receipts and recoverable records from snapshots, including after restart; an in-memory boolean is never proof of saving.

`result:save` accepts `{taskId,messageId,title,text,reviewed:true}` only for a finished local task and its latest assistant result. The title is at most 120 characters and text at most 200,000 UTF-8 bytes. It does not accept paths or project identity from the renderer. For a mission task, save its active attempt identity without changing acceptance. The explicit review authorizes saving this wording only, not mission completion or an external action. `result:recover` accepts only `{saveId}`. Every new action retains trusted-main-frame IPC validation.

Use a SHA-256 key of task, message ID, source hash, title and reviewed text for repeat requests. A repeat returns/reconciles the same operation, never a new filename. The destination is `00 Inbox/Sunny-<operation UUID>.md`; title remains in the document. Persist the complete intent synchronously before creating directories or writing the note. Write exclusively and flush the file before verifying bytes. Persist the receipt before returning saved. If receipt persistence fails, keep needs-recovery visible and preserve the original durable intent.

Pending intents become needs-recovery on startup. No startup vault write or worker retry. Explicit recovery checks the pinned vault and exact destination. Matching full bytes produce the original receipt; absence permits an exclusive write of the original reviewed text; changed/partial files, symlinks, changed vault and ambiguous errors remain needs-recovery without overwrite or alternate filename. Definite pre-write failures become failed with an explicit retry/recovery control. A temporarily absent vault is pinned through its nearest existing canonical ancestor, allowing a failed intent to retain the reviewed text; recovery requires the restored vault to resolve to that exact location. Existing saved receipts are historical verification, not a promise the note has never been edited since; checking again detects missing/changed files without recreating previously saved notes.

Expose durable records at Morgans' work desk with exact path, receipt, source task, content preview and recovery control. Disable saving until a finished reporter result is available. Editing a saved report is an explicit new reviewed version; no automatic save. Mission board reuses the existing SkillPicker keyed by mission/role, passes choices to `mission:start`, and shows confirmed skills on attempts.

## Compatibility, backup and rollback

Restore validates every operation identity, content hash, pinned path, lifecycle state and receipt before exposing state. A malformed record or duplicate operation/key fails profile loading with a preserve-profile error; it is never silently discarded or presented as saved. A `saved` record requires a matching receipt. Manual Settings exports include pending operations, reviewed text and receipts alongside the existing backup fields. The validator does not contact the vault or retry work during startup.

The new array is optional; absent means no proven saves. No existing transcript, task, approval, mission version or database table changes. Do not infer historical saves by matching titles. Intent and receipt use the same atomic JSON-row store as existing state. Fixture tests use temporary directories and both supported stores. Before activation, retain a closed-profile backup. Older binaries may drop unknown top-level fields on their next save: rollback to them must preserve a separate current-state export and receipts first. Never restore an older backup over the active profile. Reverting code does not delete notes. Save metadata is local content, included in normal backups and never transmitted to a provider.

## Alternatives and consequences

Keeping only a returned path fixes display but cannot recover a lost reply. Timestamp filenames produce duplicate notes on retry. A separate database/outbox would add a second persistence system; a durable intent in existing state meets this bounded local need. A crash during file writing can leave partial bytes; conservative recovery preserves that file and asks for inspection rather than claiming exactly-once success. This is not transactional storage across the vault and database or a power-loss guarantee for the existing state store.

## Live-discovered pre-submit recovery — 2026-10-12

The first real recovery trial found that a created provider thread with no submitted turn cannot be read or resumed after restart: `thread not loaded`, then `no rollout found`. The original user goal remains in Sunny, but its send control cannot resume this thread. Do not interpret those error strings alone as permission to retry.

Record optional `Task.launchNotSubmitted` only from a transport error explicitly proven to occur before submission. The Codex transport sets `notSubmitted` when it rejects a send before calling stdin.write because no connected child exists. Timeout, disconnect after dispatch, generic RPC rejection and old saved tasks do not gain that evidence. A new trusted IPC action `task:retryLaunch {taskId,expectedUpdatedAt}` permits a captain-clicked retry of a top-level, non-job, non-mission failed launch with this evidence. Mission and delegated tasks retain their existing attempt/coordinator controls.

Persist a reserved `retryTaskId` on the original task before dispatch, and `recoveryOfTaskId` on its replacement. An optional `launchPrompt` preserves the full goal before thread creation; the first saved user message replaces it in the same checkpoint. Keep original goal, failure and selected skill revisions, revalidate skills against the runtime, and return the same replacement on duplicate requests or a lost reply. Never automatically submit on startup. An ambiguous replacement holds its usual checkout reservation. Missing optional fields leave old tasks unchanged and ineligible; no guessed migration. All fields use the existing task JSON and normal backup. Rollback ignores optional evidence; preserve a current backup before older software rewrites state.

Tests must reject generic/uncertain failures, stale UI revisions, delegated/mission/job tasks and duplicate clicks; prove the original goal survives restart, one replacement is submitted, and failed retry checkpoints submit nothing. The live probe labels its injected pre-submit error with the same explicit evidence. This fixes the observed cause instead of treating any missing thread as safe to repeat.
